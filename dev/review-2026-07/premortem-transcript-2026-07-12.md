# Premortem transcript: washr release plan

Date: 2026-07-12
Premortemed: the three-milestone washr release plan (v1.0.2 CRAN patch, v1.1.0 metadata suite reshape, v1.2.0 feature backlog) produced by the five-reviewer panel.
Time horizon: 6 months (January 2027).
Method: 7 parallel failure investigators plus 1 adversarial counter-check, then synthesis.

## Gathered context

What: a release plan for openwashdata/washr. M1 (v1.0.2, ~2 weeks): release branch off commit 11a29c4 (the CRAN 1.0.1 state); surgical fixes for the five released bugs (#57, #58, #59, #60, setup_readme data loss), each with a regression test; CI trigger fix; NEWS/Date refresh; CRAN submission; retro-tags; pkgreview deletes its workarounds the same week. M2 (v1.1.0, ~2-3 months): metadata suite redesigned per issue #47 (auto-populated setup_metadata/update_metadata, non-interactive, Google Sheet sync removed), Imports cut 16 to ~8, behavioral test per export, end-to-end vignette, CRAN submission. M3 (v1.2.0): backlog (#13, #20, #24, #40, #56).

Who: ETH Zurich Global Health Engineering / openwashdata; maintainer of record Colin Walder (cwalder@ethz.ch); active driver Lars Schoebitz; downstream consumer is pkgreview-driven data-package releases plus the fleet of already-published openwashdata packages.

Success: 1.0.2 on CRAN within ~1 month with workarounds deleted; 1.1.0 on CRAN within ~3 months with a stable, tested, final API; no downstream release breaks in the interim.

## Failure reasons investigated

R1. The release branch became a permanent fork; 1.1.0 from main regressed bugs already fixed in 1.0.2.
R2. CRAN gatekeeping: dead maintainer email, submission confirmation stall, human review demanding unrelated compliance work, archival notice to an unwatched inbox.
R3. Nobody had the bandwidth: academic burst-contributor pattern; M2 stalls exactly like the 2025 metadata work did.
R4. The M2 redesign never converged: metadata-architecture governance debate (dataspice vs schema.org vs Zenodo vs Google Sheet) with no decision owner.
R5. Fixes designed by static analysis, shipped unverified against current cffr/desc/usethis behavior; downstream broke in a new way after workarounds were deleted.
R6. washr/pkgreview desync: workarounds deleted while old washr still resolves downstream; stamped in-flight reviews follow old checklists against new behavior.
R7. Milestone framing shipped the suite prematurely as 1.1.0; bad API public, deprecation misery, forced 2.0.0.
R8 (from counter-check). The fleet is the product: no migration story for the ~20 already-published packages whose files were generated by buggy 1.0.1 plus hand-patches; the fixed functions were never tested against that installed base.

## Deep dives

### R1: fork drift (investigator report)

THE FAILURE STORY. M1 went fine. release/1.0.2 was cut from 11a29c4, the seven fixes landed with tests, CRAN accepted 1.0.2 in early August, pkgreview deleted its workarounds. The forward-merge of release/1.0.2 into main was filed as "cleanup, this week." But main's update_citation.R had been rewritten by the metadata suite, so git merge threw conflicts across exactly the files the fixes touched. Nobody wanted to resolve conflicts against untested suite code that M2 was about to replace anyway. Decision, never written down: "we'll effectively re-do the fixes when we rebuild the metadata suite for 1.1.0." That's where it tipped. M2's setup_metadata()/update_metadata() rewrite replaced update_citation.R wholesale, and the developer re-implemented the doi-default and empty-DOI-badge behavior from memory, not from the tested 1.0.2 code. The Config/Needs/website clobber fix and CITATION.bk1 cleanup lived only on the release branch; the seven regression tests were never merged to main either, so main's CI (now finally running) was green while missing the very tests that would have caught it. 1.1.0 shipped from main in November. Within a week openwashdata's next data-package release produced a README with an empty DOI badge and a clobbered Config/Needs/website field: bugs #58 and #59, publicly announced as fixed in 1.0.2. pkgreview's workarounds were gone (version-conditioned on >= 1.0.2, which 1.1.0 satisfies). Emergency 1.1.1, CRAN cooldown friction, trust burned.

THE UNDERLYING ASSUMPTION. That the fixes' tests would travel to main automatically; the merge-back was treated as optional cleanup rather than the release's final gate.

EARLY WARNING SIGNS. (1) Two weeks after the v1.0.2 tag, git log main..release/1.0.2 is non-empty and no forward-merge PR exists. (2) Main's test suite lacks the seven 1.0.2 regression tests while M2 work is already modifying update_citation.R.

### R2: CRAN gatekeeping (investigator report)

THE FAILURE STORY. The 1.0.2 branch was ready in eleven days. Then the submission confirmation link went to cwalder@ethz.ch. Colin Walder had finished his contract at ETH in spring 2026; the mailbox bounced silently. The submission expired unconfirmed. The team only noticed when someone checked the CRAN incoming queue two weeks later. Fixing it meant a maintainer change: a documented explanation from the new maintainer plus a resubmission with changed Authors@R. That exchange took three weeks over the summer lull. The resubmission cleared automated pretests with one NOTE, "New maintainer," which mandatorily routes to human inspection. The reviewer, looking at a package untouched for 20 months, didn't limit herself to the diff: replace blanket dontrun with executable examples or donttest; add missing value tags; do not write to the user's filespace (the dontshow devtools::create(tempdir()) calls tripped the check-time policy). The surgical patch became a documentation rewrite across 17 man pages. Two resubmission cycles later it was late October. Meanwhile a routine CRAN check deadline email had gone to the dead inbox; washr was archived on September 16. Un-archiving required passing current incoming checks cleanly. pkgreview's workarounds never came out; M2 never started.

THE UNDERLYING ASSUMPTION. That CRAN would evaluate the patch diff, delivered promptly to a monitored maintainer, rather than re-reviewing the whole stale package through a dead email address.

EARLY WARNING SIGNS. (1) Test email to cwalder@ethz.ch bounces, or Colin absent from recent repo activity. (2) Submission sits pending confirmation beyond 48 hours.

### R3: bandwidth stall (investigator report)

THE FAILURE STORY. The repo's history already contained this failure, twice. July 2024: a CRAN push stalls mid-summer and has to be rescued three months later by cherry-picking "different parts of different commits from the cran branch committed between July 4 and July 30." Nov-Dec 2024: the metadata suite is built in a five-week solo burst, then the author vanishes from the log; the work sits unmerged until PR #46 lands in May 2025 and that contributor also disappears. Every contributor appears as a one-burst student and exits. Nobody has ever shipped a second CRAN release. July 2026 replayed the pattern. Lars filed issues #57-60 in a single hour on July 8, an AI session produced the plan, and M1 rode that anger: the five fixes were surgical, most merged by August. Then the tip: CRAN submission is the step requiring sustained human attention (email round-trips, resubmission), and it collided with the September semester start and fieldwork. 1.0.2 became "merged, will submit next week." M2, a redesign with de-interactivization, dependency cuts and a test suite, needed a dedicated contributor, and the group's staffing model produces contributors only in bursts. None materialized. By January 2027 main holds the unreleased suite plus unreleased fixes; pkgreview kept its workarounds because deleting them was gated on a CRAN release that never happened; the next data-package release filed issues #61-64. Precedent: the July 22, 2025 issue-triage burst also produced zero commits afterwards.

THE UNDERLYING ASSUMPTION. That a plan sized in engineer-weeks would be executed by an institution that has only ever produced work in unstaffed, non-recurring student bursts.

EARLY WARNING SIGNS. (1) 1.0.2 fixes merged but no CRAN submission within two weeks of the last merge. (2) No commit from anyone other than Lars in the first month; pkgreview workarounds still present by September 2026.

### R4: redesign never converged (investigator report)

THE FAILURE STORY. M1 shipped on time; M2 died in design review. The first fork appeared in week one: setup_metadata() needed a canonical source of truth, and there were four candidates already in production: DESCRIPTION's Authors@R, dataspice's creators.csv, the org Google Sheet feeding the openwashdata website catalog, and the Zenodo/DataCite records raised in #56 (filed four days before this plan, assigned to Lars, while #47 sat assigned to someone else: two owners, two directions). Every draft PR reopened the same question: if the sheet drives the website and Zenodo drives DOIs, what is the JSON-LD for? Nobody could answer without deciding the org's metadata architecture, which was nobody's job. The second fork was migration: two packages had already run add_metadata() and hand-edited the four CSVs; deleting dataspice meant discarding those edits or writing a converter for exactly two packages, a week of argument either way. Meanwhile FAIR ambitions kept enlarging scope ("if we're redesigning anyway, shouldn't it emit DataCite-compatible fields so #56 becomes trivial?"). Each meeting ended with a broader spec, not a decision. By October the design doc had three competing field mappings and no owner empowered to pick one. The old 8-export suite stayed on main; three new data packages half-ran it in the interim, growing the migration surface. January 2027: 1.1.0 unreleased, #47 still open, now with 14 comments.

THE UNDERLYING ASSUMPTION. That "auto-populate from DESCRIPTION + dictionary.csv" was an implementation detail rather than a decision about which of four live metadata systems is canonical, a governance call the plan assigned to no one.

EARLY WARNING SIGNS. (1) The setup_metadata() design issue accumulates comments referencing #56, the website catalog, or FAIR/fairenough instead of function signatures within two weeks. (2) New data packages still running old add_metadata() after M1, with no interim guidance freezing usage.

### R5: unverified fixes (investigator report)

THE FAILURE STORY. The v1.0.2 fixes were written against washr's Nov 2024 dependency floor, but CI installed current CRAN packages, and cffr had moved on. The .bk1 cleanup and the doi=NULL guard were coded to the imagined cffr 1.x behavior: the regression test asserted "no inst/CITATION.bk1 after update_citation()", which passed vacuously because 2026 cffr no longer writes .bk1 at all. What nobody observed, because nothing was ever executed during design, was that the delete-before-write workaround now handed cff_write_citation() a missing-file path, and with doi=NULL the new cffr validated the keys list and silently dropped the doi/identifiers entry, emitting a structurally different CITATION.cff. Tests compared fields the fix touched, not the whole file. CI green, CRAN accepted 1.0.2. Second mechanism: the Config/Needs/website fix used desc::desc_set() to merge fields back, and desc rewrites the whole file, reflowing Authors@R and reordering fields. pkgreview's checklists relied on "diff DESCRIPTION after update_description()" as the verification step; with the 1.0.1 caveats deleted the week 1.0.2 landed, that safety diff was gone. Release day for the next data package: /create-release runs update_citation(doi = NULL); the skill no longer deletes .bk1 or strips the empty badge, trusting 1.0.2. The package ships to Zenodo with a CITATION.cff missing its identifier block and a DESCRIPTION reflowed so the metadata checklist's diff check flags 40 spurious lines. The reviewer can't tell real regressions from formatting noise, hand-edits both files, and the review takes longer than under 1.0.1-with-workarounds. Two maintainers quietly pin washr 1.0.1.

THE UNDERLYING ASSUMPTION. That third-party package behavior recalled from a Nov 2024 snapshot still held in mid-2026, and that tests asserting the imagined behavior would fail if it didn't.

EARLY WARNING SIGNS. (1) Regression tests that pass on first run without the fix applied (vacuous assertions). (2) CI never exercising the interactive/doi=NULL release path, or no full-file CITATION.cff/DESCRIPTION snapshot diff.

### R6: downstream desync (investigator report)

THE FAILURE STORY. October 2026. washr 1.0.2 ships to CRAN; the same week pkgreview strips the "washr 1.0.1 caveats" from create-release, add-doi and standards.md, bumps VERSION, closes #23. Fixture verification passes on a maintainer laptop with fresh washr 1.0.2. Release day for the next data package comes three weeks later. The reviewer's session runs in a CI image whose R library was baked in September: washr resolves to 1.0.1 (CRAN binary lag plus a cached renv.lock pinning 1.0.1; nothing anywhere pins or even checks the washr version, because the contract between the two ecosystems was only ever prose in the caveats that just got deleted). update_citation() silently injects the empty DOI badge and drops inst/CITATION.bk1; update_description() strips Config/Needs/website. The skill no longer says to look for any of this, so the session commits it. The pkgdown deploy fails (missing website deps), and the published README carries a dead DOI badge. Worse: an in-flight review stamped on standard 1.0.0 fetches the old checklists, which still mandate deleting "the broken empty DOI badge", while running the new skills. On a machine that did get 1.0.2, the session dutifully deletes the now-correct DOI badge, re-breaking a README that washr had finally gotten right. Two packages ship broken in opposite directions in the same week.

THE UNDERLYING ASSUMPTION. That the CRAN release and the deletion of pkgreview's caveats would take effect atomically everywhere, when nothing (no version pin, no packageVersion("washr") guard in any skill) enforced which washr a review session actually loads.

EARLY WARNING SIGNS. (1) CITATION.bk1 files or empty DOI badges appearing in post-cleanup release PRs (proves 1.0.1 still in the wild). (2) Stamped in-flight reviews still open when VERSION bumps, with no note reconciling old checklists against new skill behavior.

### R7: milestone pressure ships the suite (investigator report)

THE FAILURE STORY. M2's title did the damage before any code did. "1.1.0 on CRAN with stable, tested, final API" made shipping the success criterion, not deciding whether to ship. Issue #47, the maintainer's own doubt about whether add_metadata() should exist, was closed in week one as "resolved by M2", converting an open design question into a delivery commitment. From that moment the redesign was a rewrite-with-a-deadline. The corners fell in a predictable order. Auto-population was implemented for the easy DESCRIPTION fields and stalled on the hard ones (variable-level dictionaries), so readline() prompts came back "as fallback". The Google Sheet sync, which the panel said to remove, survived behind sync = FALSE, because deleting it meant admitting two months of 2025 work was sunk cost. Tests were written against current behavior to turn the milestone green, enshrining the bugs rather than probing them. Around month 2.5, with a FAIR-data grant report wanting "metadata automation shipped", someone said "we can fix the defaults in 1.1.1". That was the moment the wrong default became permanent: CRAN publication turned every argument name, every prompt, every export into a contract. By January 2027 the org maintains eight public exports it privately wants to delete, fields deprecation-warning complaints from the three real users of setup_metadata, and is drafting a 2.0.0 breaking release, the exact outcome the milestone structure existed to prevent. Every milestone closed on time.

THE UNDERLYING ASSUMPTION. That putting "on CRAN" in the milestone's success criterion would motivate quality, when it actually made shipping, not redesign adequacy, the thing being measured.

EARLY WARNING SIGNS. (1) Issue #47 closed by milestone assignment rather than by a written design decision. (2) Sheet-sync demoted to an argument/flag instead of deleted; "temporary" code surviving the first M2 review.

### R8: the fleet is the product (adversarial counter-check)

THE MISSING FAILURE MODE. Every milestone treats washr the tool as the deliverable. But washr's entire value is the ~20+ already-published openwashdata data packages whose DESCRIPTION, CITATION.cff and READMEs were generated by the buggy 1.0.1 and then hand-patched (partly via pkgreview's workarounds). Fixing update_citation/update_description does nothing until someone re-runs them across that fleet, and re-running the fixed functions on files shaped by the buggy version plus manual patches is exactly the case none of the seven regression tests cover. They test pristine fixtures. On real packages, the fixed code will diff against hand-corrections, regenerate CITATIONs that disagree with Zenodo DOIs already minted and immutable, and force a fleet-wide re-release nobody scoped, budgeted or even listed as a milestone item.

WHY IT WAS OVERLOOKED. All seven failure modes are tool-repo-centric (branches, CRAN, pkgreview, API design). Five reviewers converged on "will the release ship correctly" and nobody asked "then what happens when it touches the packages that already exist": the classic groupthink of testing the fix, not the installed base.

THE FAILURE STORY. v1.0.2 ships clean, all seven tests green, workarounds deleted, everyone celebrates. Three weeks later a student re-reviews an older data package and runs update_citation(). It "corrects" the DOI format, breaking agreement with the Zenodo record and the citation already circulating in a published paper, and clobbers two fields the team had hand-fixed in 2025. The team's response is rational and fatal: an informal rule spreads, "don't run washr's update functions on existing packages". washr becomes setup-only scaffolding. With the update path distrusted, M2's redesigned metadata suite has no consumers, the rationale for 1.1.0 evaporates, and the plan dies not from a failed release but from a successful one that nobody dares apply.

EARLY WARNING SIGNS. (1) No test in the M1 branch feeds update_* a file emitted by 1.0.1 or a hand-patched real package. (2) No issue, checklist item or milestone anywhere naming the existing published packages or a re-run/re-release plan for them.
