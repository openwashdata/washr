Premortem: the washr release plan

openwashdata/washr · plan: v1.0.2 CRAN patch, then v1.1.0 metadata-suite reshape, then v1.2.0 backlog · 7 failure investigators + 1 adversarial counter-check · 2026-07-12
The frame: it is January 2027, six months from now. The plan has failed. 1.0.2 never deleted the downstream workarounds, or 1.1.0 never shipped, or something shipped and made things worse. We looked back and worked out why.
Most likely failure

R3: Nobody had the bandwidth

The repo's own history is the base rate: every contributor since 2024 appears as a one-burst student and exits; a CRAN push already stalled once mid-2024 and needed a three-month rescue; the metadata suite itself sat unmerged for six months; nobody has ever shipped a second CRAN release. The plan is sized in engineer-weeks for an institution that produces work in unstaffed bursts. The likely tipping point: fixes merged, but the CRAN submission (the step needing sustained human attention) slides past semester start and never happens.

Most dangerous failure

R5 + R8: Unverified fixes meet the untested fleet

The fixes were designed by static analysis in an environment with no R interpreter, against dependency behavior remembered from Nov 2024. If they ship unverified, tests can pass vacuously while behavior differs, and the first victim is the installed base: ~20 published data packages whose files were generated by buggy 1.0.1 plus hand-patches. Re-running "fixed" functions there can clobber hand-corrections and regenerate CITATIONs that disagree with immutable Zenodo DOIs, after the pkgreview safety-net workarounds were already deleted. Failure by successful release.

The hidden assumption

"Merging correct code equals delivering the fix." Every part of the original plan stops at the repo boundary. But delivery actually runs through four unverified channels: a CRAN maintainer email that may be dead (R2), dependency behavior that was never executed (R5), whichever washr version a downstream session actually resolves (R6), and a fleet of already-published packages that no fix reaches without a migration step nobody scoped (R8). The plan verified the code and assumed the channels.

The revised plan (changes mapped to failure modes)

  1. Gate 0, this week [R2]: verify cwalder@ethz.ch is monitored before any code is written; if not, prepare the maintainer change to ride the 1.0.2 submission. Confirm who receives CRAN check emails.
  2. Fail-first tests on a real R toolchain [R5]: before coding fixes, reproduce all five bugs with current CRAN cffr/desc/usethis and record actual behavior. Every regression test must demonstrably fail on unfixed 1.0.1 code. Add full-file snapshot tests for DESCRIPTION and CITATION.cff, not just the touched fields.
  3. Fleet fixture and pilot [R8]: add a test fixture copied from a real published package as shipped (1.0.1-generated, hand-patched). After CRAN acceptance, re-run the fixed functions on one older package and write a re-run playbook before pkgreview changes anything.
  4. Forward-merge gate [R1]: the release/1.0.2 to main merge PR (fixes plus tests) must be green before the CRAN submission is sent, not after.
  5. Version-conditioned caveats, not deletion [R6]: pkgreview skills check packageVersion("washr") at runtime; 1.0.1 caveats stay active below 1.0.2. Full removal only after two consecutive clean downstream releases.
  6. Decision before code in M2 [R4, R7]: issue #47 is closed by a one-page design decision with a named owner (Lars) and a 4-week deadline, not by milestone assignment. M2's success criterion is reworded: implementing the decision, with an explicit ship/defer point. Shipping 1.1.0 as a cleanup-only minor without the suite counts as success. The Google Sheet sync is deleted, not flag-gated.
  7. Burst-compatible sizing [R3]: every M1 issue is one-session-sized and independently shippable; if the timeline slips, scope cuts to the four bug fixes plus submission, nothing else.

Kill criteria

  • If the CRAN submission is not confirmable within 2 weeks (maintainer unreachable), stop the CRAN track: distribute via GitHub release + r-universe for downstream and run the maintainer change in parallel.
  • If 1.0.2 is merged but unsubmitted 2 weeks after branch-ready, the bandwidth failure is happening: cut scope to bugfixes + submission only, drop everything else from M1.
  • If the #47 design decision is not written and agreed within 4 weeks of 1.0.2 shipping, the metadata suite is out of 1.1.0; 1.1.0 ships as a dependency-cleanup minor.
  • If git log main..release/1.0.2 is non-empty two weeks after the v1.0.2 tag, freeze M2 work until the forward-merge lands.

Pre-launch checklist (v1.0.2)

  • Maintainer email verified reachable, or maintainer change prepared in Authors@R and explained in cran-comments.md.
  • Each regression test proven to fail on the unpatched 1.0.1 branch point (fail-first evidence in each PR).
  • Real-fleet fixture test green: fixed functions run on a copy of a published package's actual files with only intended diffs, DOI agreement with Zenodo preserved.
  • R CMD check --as-cran clean on the exact tagged commit with current CRAN dependencies; dontshow tempdir landmines removed; Date fresh; NEWS entry present.
  • Forward-merge PR to main open and green before submission.
  • pkgreview change ready but gated on packageVersion, verified against fixtures/pkgreviewtest; caveats not yet deleted.

Verdict on "should I update the CRAN package?"

Yes, but only the surgical 1.0.2 patch, and only after Gate 0 (maintainer channel verified) and the fail-first test evidence exist. The four reported bugs plus the setup_readme data-loss bug are all in the CRAN 1.0.1 tarball, downstream consumes washr from CRAN, so a CRAN patch is the only action that deletes the pkgreview workarounds. Do not let the unreleased metadata suite anywhere near this submission.

The eight failure modes

R3: Bandwidth stall likely + severe

Investigator 3 · institutional

M1 rides the anger of the July 8 bug-filing burst; fixes merge by August. Then CRAN submission (email round-trips, resubmissions) collides with semester start and fieldwork. "Merged, will submit next week" becomes January. The repo has seen this twice before: the 2024 cran-branch rescue and the metadata suite's six unmerged months.

Assumption

A plan sized in engineer-weeks executed by an institution that works in unstaffed student bursts.

Early warnings

Fixes merged, no submission within 2 weeks. No commits from anyone but Lars in month one.

R2: CRAN gatekeeping likely + severe

Investigator 2 · process

The confirmation link goes to cwalder@ethz.ch; the contract ended in spring; the mailbox bounces silently. Maintainer change takes weeks; the "New maintainer" NOTE routes to human review; the reviewer re-reviews the whole 20-month-old package (blanket dontrun, missing value tags, tempdir writes). A check-deadline email to the dead inbox archives the package mid-plan.

Assumption

CRAN evaluates the diff, delivered to a monitored maintainer, rather than re-reviewing a stale package via a dead address.

Early warnings

Test email bounces. Submission pending confirmation beyond 48 hours.

R8: The fleet is the product counter-check find

Adversarial counter-check · blind spot

All seven other modes are tool-repo-centric. The value of washr is ~20 published packages whose files were generated by buggy 1.0.1 plus hand-patches. The fixed functions were only ever tested on pristine fixtures. First re-run on an old package "corrects" a CITATION against an immutable Zenodo DOI and clobbers 2025 hand-fixes; the team's rational response, "never run update functions on existing packages", kills the update path and with it the rationale for 1.1.0.

Assumption

Fixing the tool fixes the ecosystem; nobody scoped what happens when fixed code touches the installed base.

Early warnings

No test feeds update_* a 1.0.1-emitted or hand-patched file. No issue names the existing packages.

R5: Unverified fixes less likely + severe

Investigator 5 · technical

Fixes coded to imagined Nov 2024 cffr/desc behavior; 2026 cffr differs; the .bk1 regression test passes vacuously; desc_set reflows the whole DESCRIPTION. pkgreview deleted its caveats on schedule, so release day produces a CITATION.cff missing its identifier block and 40 lines of formatting noise in the checklist diff. Two maintainers quietly pin washr 1.0.1. Worse than before the patch.

Assumption

Dependency behavior recalled from a snapshot still holds, and tests asserting imagined behavior would fail if it did not.

Early warnings

A regression test that passes before the fix is applied. No full-file snapshot diffs in CI.

R1: Fork drift less likely + severe

Investigator 1 · process

The forward-merge of release/1.0.2 into main conflicts with suite code and gets deferred ("we'll redo it in the 1.1.0 rewrite"). M2 re-implements the fixes from memory; the seven regression tests never reach main; 1.1.0 ships and re-breaks #58/#59, publicly announced as fixed, with workarounds gone (version-conditioned on >= 1.0.2, which 1.1.0 satisfies).

Assumption

The merge-back was optional cleanup rather than the release's final gate.

Early warnings

main..release/1.0.2 non-empty two weeks post-tag. M2 edits update_citation.R while main lacks the regression tests.

R7: Milestone pressure ships the suite less likely + severe

Investigator 7 · incentive

"1.1.0 on CRAN" as the success criterion converts #47 from an open question into a delivery commitment. Auto-population covers the easy fields, readline returns "as fallback", the sheet-sync survives behind sync = FALSE, tests are written to pass. CRAN publication freezes the half-baked API; 2027 is spent on deprecation cycles toward the 2.0.0 the plan existed to avoid. Every milestone closed on time.

Assumption

Putting "on CRAN" in the milestone measures quality when it actually measures shipping.

Early warnings

#47 closed by milestone assignment, not a written decision. Sheet-sync demoted to a flag instead of deleted.

R4: Redesign never converges likely + moderate

Investigator 4 · governance

setup_metadata() needs a canonical source of truth and there are four live candidates (Authors@R, creators.csv, the org Google Sheet, Zenodo/DataCite via #56, with #47 and #56 assigned to different owners). Every draft PR reopens the architecture question; FAIR ambitions widen the spec each meeting; by October there are three competing field mappings and no empowered owner. 1.1.0 never ships; the buggy suite keeps accreting users on main.

Assumption

"Auto-populate from DESCRIPTION + dictionary" is an implementation detail, not an unowned governance decision between four live systems.

Early warnings

Design thread cites the website catalog, FAIR or #56 instead of signatures within two weeks. New packages still running old add_metadata().

R6: Downstream desync moderate + moderate

Investigator 6 · ecosystem

pkgreview strips its caveats the week 1.0.2 lands; three weeks later a review session runs on a September CI image resolving washr 1.0.1 (binary lag, cached renv.lock; nothing pins or checks the version). Old bugs fire with no workaround text left. Meanwhile an in-flight review stamped on the old standard deletes the now-correct DOI badge on a machine that did get 1.0.2. Two packages break in opposite directions in one week.

Assumption

The CRAN release and caveat deletion take effect atomically everywhere, with no version guard anywhere.

Early warnings

CITATION.bk1 or empty badges in post-cleanup PRs. Stamped in-flight reviews open across the VERSION bump.
